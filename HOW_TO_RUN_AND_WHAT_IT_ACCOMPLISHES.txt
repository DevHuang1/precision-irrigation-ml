1. PROJECT OVERVIEW
================================================================================

This repository implements a complete machine-learning pipeline for an
"AI-Powered Precision Irrigation" system. The goal is to help vegetable
farmers decide WHEN to irrigate, using low-cost sensors and a small,
edge-deployable ML model — improving water-use efficiency without needing
expensive cloud infrastructure.

Because no real field data exists yet, the pipeline is built and validated
against a realistic SYNTHETIC dataset that follows the schema described in
Section 5.1 of the research plan. The pipeline is deliberately structured so
that real sensor data can be dropped in later with ZERO code changes.

The core scientific question the project answers:
    "Can a simple ML model beat a naive threshold rule
     (e.g. 'irrigate when soil_moisture < X')?"

This is an honest, falsifiable benchmark — the README explicitly warns that
if an ML model cannot beat a simple threshold rule, that is a finding worth
reporting honestly rather than hiding.

  After activation, your prompt should show (.venv) at the start.

3. THE FULL PIPELINE, STEP BY STEP
================================================================================

Run these commands IN ORDER, from the project root:

  # Step 1 — Generate synthetic sensor data
  python -m data.synthetic_generator

  # Step 2 — Clean & feature-engineer the data
  python -m src.data_pipeline

  # Step 3 — (Optional) Hyperparameter tuning
  python -m src.tune

  # Step 4 — Train the models
  python -m src.train

  # Step 5 — Evaluate the models
  python -m src.evaluate

  # Step 6 — Export the best model for edge deployment
  python -m src.export_edge_model

  # Step 7 — Export the farmer guidance feed
  python -m src.export_farmer_feed

  # Step 8 — Run the unit tests
  pytest

  # Bonus — Launch the monitoring dashboard
  cd dashboard && npm install && npm run dev   # then open http://localhost:3000


================================================================================
4. WHAT EACH STEP ACCOMPLISHES (DEEP DIVE)
================================================================================

--------------------------------------------------------------------------------
STEP 1: python -m data.synthetic_generator
--------------------------------------------------------------------------------
WHAT IT DOES:
  Generates ~90 days of synthetic sensor readings at 30-minute intervals for
  two plot types: "treatment" and "control".

WHAT IT ACCOMPLISHES:
  * Creates data/raw/synthetic_sensor_log.csv with 8,640 rows.
  * Each row contains realistic sensor readings:
      - timestamp, plot_id
      - soil_moisture_pct, soil_temp_c
      - air_temp_c, air_humidity_pct
      - rainfall_mm_24h, days_since_planting
      - crop_growth_stage, water_applied_l
      - irrigated_next_flag (the LABEL we want to predict)
  * The label balance is reported (e.g. "13.3% positive"), meaning only
    ~13% of rows represent an irrigation event. This class imbalance is
    realistic and important — it's why accuracy alone is misleading.

WHY IT MATTERS:
  This gives us a realistic, reproducible dataset to build and validate the
  ML pipeline before real field data is available.

--------------------------------------------------------------------------------
STEP 2: python -m src.data_pipeline
--------------------------------------------------------------------------------
WHAT IT DOES:
  Reads the raw CSV, cleans it, and engineers features.

WHAT IT ACCOMPLISHES:
  * CLIPPING: Out-of-range sensor readings are clipped to realistic bounds
    defined in SENSOR_BOUNDS (e.g. soil moisture 0-100%).
  * INTERPOLATION: Missing values are linearly interpolated within each plot.
  * FEATURE ENGINEERING — automatically derives new columns:
      - time_of_day_*  (hour-of-day one-hot features)
      - lagged soil moisture (past values, e.g. 1-step, 3-hour lags)
      - rolling rainfall (3-hour rolling window)
      - growth-stage one-hot encoding
  * Writes data/processed/features.csv (8,636 rows x 20 columns).

WHY IT MATTERS:
  This is where raw sensor data becomes ML-ready. The derived features
  (especially soil-moisture history/lags) are expected to dominate model
  importance — matching the research finding that soil-moisture history
  beats a full evapotranspiration model.

--------------------------------------------------------------------------------
STEP 3: python -m src.tune  (OPTIONAL)
--------------------------------------------------------------------------------
WHAT IT DOES:
  Runs RandomizedSearchCV with TimeSeriesSplit cross-validation.

WHAT IT ACCOMPLISHES:
  * Tunes hyperparameters for logistic regression, random forest, and xgboost.
  * Uses TimeSeriesSplit instead of standard k-fold to avoid LEAKAGE —
    random shuffling would let future information leak into training and
    inflate accuracy. Chronological splitting is the honest approach.
  * Saves tuned models to models/tuned_*.joblib.

WHY IT MATTERS:
  Proper tuning with time-aware splitting ensures the reported performance
  is realistic and not an artifact of data leakage.

--------------------------------------------------------------------------------
STEP 4: python -m src.train
--------------------------------------------------------------------------------
WHAT IT DOES:
  Trains 4 models on the chronological train split (first 70% of data).

WHAT IT ACCOMPLISHES:
  * baseline          — a simple threshold rule (soil_moisture < X)
  * logistic_regression
  * random_forest
  * xgboost
  * If tuned models exist, they are used automatically.
  * Saves each trained model to models/*.joblib.

WHY IT MATTERS:
  The baseline is the critical reference point. Every ML model must be
  compared against it. If ML can't beat a simple threshold, that's an honest
  finding.

--------------------------------------------------------------------------------
STEP 5: python -m src.evaluate
--------------------------------------------------------------------------------
WHAT IT DOES:
  Evaluates all models on the held-out CHRONOLOGICAL test set (last 15%).

WHAT IT ACCOMPLISHES:
  * Prints a per-class classification report for each model.
  * Writes results/model_comparison.csv — accuracy, precision, recall, F1
    PER CLASS, sorted by macro-F1.
  * Writes results/feature_importance.png — built-in tree importances.
  * Writes results/test_predictions.csv.
  * Identifies and reports the BEST model by macro-F1.

WHY IT MATTERS:
  Because "don't_irrigate" is the majority class, accuracy alone is
  misleading. Per-class metrics (especially recall on the minority
  "irrigate" class) tell the real story. Macro-F1 balances both classes.

--------------------------------------------------------------------------------
STEP 6: python -m src.export_edge_model
-------------------------------------------------------------------------------
WHAT IT DOES:
  Exports the best model for deployment on low-cost edge hardware.

WHAT IT ACCOMPLISHES:
  * Writes edge/exported/best_model.joblib
  * Best-effort writes edge/exported/best_model.onnx (if onnx/skl2onnx
    installed)
  * Prints file sizes in KB — evidence of edge deployability.

WHY IT MATTERS:
  A model that's accurate but too large won't run on a Raspberry Pi or
  ESP32. Reporting size in KB is part of the deployability evidence.
  (In our run: 2.4 KB joblib, 1.9 KB ONNX — very edge-friendly.)

-------------------------------------------------------------------------------
STEP 7: python -m src.export_farmer_feed
-------------------------------------------------------------------------------
WHAT IT DOES:
  Turns the trained model into plain-language guidance for the farmer.

WHAT IT ACCOMPLISHES:
  * Runs the best model on the most recent sensor readings for every plot.
  * Writes results/farmer_feed.json with, per plot:
      - a recommendation ("Water now" / "No watering needed")
      - the reasoning in plain language (e.g. "Soil moisture is 55% — your
        crops have enough water for now")
      - a suggested water amount (average applied per growth stage)
      - current conditions, a 7-day moisture trend, and recent watering
      - a growth-stage-specific watering tip
  * Also writes results/sim_model.json — the exported logistic-regression
    weights (scaler, coefficients, feature list) used by the dashboard's
    SIMULATION MODE, so scenario tweaking runs instantly in the browser with
    no Python server required.
  * These files power the /farmer view of the dashboard.

WHY IT MATTERS:
  The ML output needs to be actionable, not just a number. The farmer view
  translates model predictions into a clear decision with the why, and the
  simulation mode lets researchers explore "what if" scenarios live.

-------------------------------------------------------------------------------
STEP 8: pytest
-------------------------------------------------------------------------------
WHAT IT DOES:
  Runs the unit test suite.

WHAT IT ACCOMPLISHES:
  * Verifies the pipeline components work correctly.
  * In our run: 5 tests passed.


WHY IT MATTERS:
  Automated tests protect against regressions and give confidence the
  pipeline is correct and reproducible.

--------------------------------------------------------------------------------
BONUS: cd dashboard && npm install && npm run dev  (then open http://localhost:3000)
-------------------------------------------------------------------------------
WHAT IT DOES:
  Launches an interactive, browser-based monitoring dashboard built with
  Next.js (React + TypeScript).

WHAT IT ACCOMPLISHES:
  * The dashboard exposes JSON API endpoints that read the pipeline
    outputs directly from disk:
        /api/raw         -> data/raw/synthetic_sensor_log.csv
        /api/processed   -> data/processed/features.csv
        /api/results     -> results/model_comparison.csv
        /api/farmer-feed -> results/farmer_feed.json
  * TWO views, switchable from the top navigation:
      /farmer  — a human-understandable view for the farmer: a big
                 "Water now" / "No watering needed" recommendation per plot,
                 the reason in plain language, a suggested water amount,
                 current conditions, a 7-day soil-moisture trend, and the
                 last watering events.
      /        — the technical view: daily soil-moisture line chart per
                 plot, engineered-feature table, and per-model comparison
                 (macro-F1).
  * No manual refresh needed: the API routes are dynamic, so running the
    pipeline again and reloading the page shows the new numbers.
  * Useful for demonstrating the project and for future field monitoring.

5. THE RESULTS & HOW TO INTERPRET THEM
================================================================================

RESULTS FROM THE ACTUAL RUN (chronological test set, sorted by macro-F1):

  Model               Accuracy  Prec(irrigate)  Recall(irrigate)  Macro-F1
  ------------------  --------  --------------  ----------------  --------
  logistic_regression   0.878        0.378            1.000         0.739
  random_forest         0.800        0.270            1.000         0.652
  xgboost               0.795        0.266            1.000         0.648
  baseline (threshold)  0.793        0.264            1.000         0.646

KEY OBSERVATIONS:
  1. BEST MODEL: logistic_regression wins with macro-F1 0.739.
  2. IT BEATS THE BASELINE: The ML model (0.739) outperforms the simple
     threshold rule (0.646) — this is the honest, headline finding the
     project is designed to produce.
  3. RECALL ON "IRRIGATE" IS 1.000 for ALL models: Every model catches
     every irrigation event. This is good for not missing irrigations.
  4. PRECISION ON "IRRIGATE" IS LOW (0.27-0.38): Models over-predict
     irrigation (many false positives). This is the classic trade-off when
     you maximize recall on a rare class. In practice, false-positive
     irrigations waste a little water; false-negatives (missed irrigations)
     could stress crops — so favoring recall is a sensible design choice.
  5. CLASS IMBALANCE IS VISIBLE: "don't_irrigate" has ~1199 test samples vs
     only ~96 "irrigate" — hence accuracy alone (0.79-0.88) looks high but
     hides the minority-class story. Macro-F1 is the honest metric.

WHAT THE FEATURE IMPORTANCE PLOT SHOWS:
  Past soil moisture and its lags are expected to dominate — confirming the
  research finding that soil-moisture history beats a full
  evapotranspiration model. (See results/feature_importance.png.)

6. EDGE DEPLOYMENT & REAL-WORLD USE
================================================================================

The exported model (edge/exported/best_model.joblib / .onnx) is tiny
(< 2.5 KB), making it suitable for low-cost hardware:

  * edge/inference_service.py — a Raspberry-Pi-side inference stub with a
    rule-based safety fallback when the model is unavailable or readings
    are out of range.
  * For microcontroller-class devices (ESP32), the README suggests
    micromlgen/m2cgen to transpile a small tree ensemble into C, or running
    the model on a companion Pi that the ESP32 reports to.

This demonstrates the full journey: sensor data -> ML model -> tiny
deployable artifact that can run on cheap hardware in the field.

7. SWAPPING IN REAL FIELD DATA
================================================================================

When real field data becomes available, NO CODE CHANGES are needed if the
CSV has exactly these columns:

  timestamp, plot_id, soil_moisture_pct, soil_temp_c, air_temp_c,
  air_humidity_pct, rainfall_mm_24h, days_since_planting,
  crop_growth_stage, water_applied_l, irrigated_next_flag

Then simply:

  cp your_field_data.csv data/raw/synthetic_sensor_log.csv
  python -m src.data_pipeline && python -m src.train && python -m src.evaluate

Notes:
  * Derived features (time_of_day, lags, rolling rainfall, growth-stage
    one-hots) are computed automatically — don't add them to the CSV.
  * If the sampling interval differs from 30 min, pass --interval-min <n>
    to src.data_pipeline so the 3-hour rolling window is correct.
  * Growth stages must map to the four known ones
    (establishment/vegetative/flowering/maturity) or the one-hot encoding
    will break.

9. TROUBLESHOOTING & COMMON ISSUES
================================================================================

  * "python: command not found" / wrong version
      -> Use the venv: source .venv/bin/activate
      -> Or call .venv/bin/python explicitly.

  * ModuleNotFoundError
      -> Dependencies not installed. Run: pip install -r requirements.txt

  * ONNX export skipped
      -> onnx/skl2onnx not installed. The script falls back to joblib-only
         (still works fine). Install with: pip install onnx skl2onnx

  * Growth-stage encoding error with real data
      -> Map your stages to the four known ones or extend GROWTH_STAGES.

  * Wrong rolling-window with different sampling interval
      -> Pass --interval-min <n> to src.data_pipeline.
