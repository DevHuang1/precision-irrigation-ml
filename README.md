# precision-irrigation-ml

ML pipeline for *"AI-Powered Precision Irrigation for Sustainable Vegetable
Farming — Improving Water-Use Efficiency Through Low-Cost Edge Machine
Learning."*

No real field data exists yet, so the pipeline is built and validated against a
realistic **synthetic dataset** (Section 5.1 schema) and structured so real
sensor data drops in with zero code changes.

## Datasets

See [datasets.md](datasets.md) for detailed descriptions of each raw and converted dataset, including source, date ranges, spatial/temporal resolution, and conversion notes.

Quick links:
- [Synthetic](#synthetic) — generated on-the-fly for development and testing
- [FBK Soil Moisture Consortium](#fbk-soil-moisture-consortium) — Hugging Face, multi-consortium daily sensors
- [Zenodo Cotton](#zenodo-cotton) — IoT device + NDVI daily aggregates
- [UniPR Tomato (Stuard)](#unipr-tomato-stuard) — Mendeley, 3-line ~10-min sensor platform
- [UniPR Tomato Evolving](#unipr-tomato-evolving) — Mendeley, multi-year multi-sensor time series

## Quick start

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python -m data.synthetic_generator          # -> data/raw/synthetic_sensor_log.csv
python -m src.data_pipeline                 # -> data/processed/features.csv
python -m src.tune                          # optional: TimeSeriesSplit tuning
python -m src.train                         # -> models/*.joblib
python -m src.evaluate                      # -> results/model_comparison.csv, feature_importance.png
python -m src.export_farmer_feed            # -> results/farmer_feed.json (farmer view data)
python -m src.export_edge_model             # -> edge/exported/best_model.joblib (+ .onnx if available)
pytest                                      # unit tests
```

## Dashboard (Next.js)

```bash
cd dashboard && npm install && npm run dev  # -> http://localhost:3000
```

Two views, switchable from the top navigation:

* **`/farmer`** — a plain-language view for the farmer: a "water now / no
  watering needed" recommendation per plot, the reason in human terms, a
  suggested water amount, current conditions, a 7-day soil-moisture trend and
  watering history. Backed by `results/farmer_feed.json`, generated by
  `python -m src.export_farmer_feed` from the trained model.
  * **Simulation mode** (toggle in the top-right): tweak live conditions
    (soil moisture, temperature, humidity, rainfall, growth stage, time of
    day) with sliders and watch the model's recommendation — and a
    probability-vs-moisture sensitivity curve — update instantly. Great for
    demonstrating the model to researchers. The scoring runs in the browser
    from `results/sim_model.json` (exported logistic-regression weights, so
    no Python server needed) and matches the Python model exactly.
* **`/`** — the technical view: soil-moisture line chart, engineered-feature
  table, and the per-model comparison.

The dashboard reads the pipeline outputs (`data/` and `results/` CSVs) via
`/api/raw`, `/api/processed`, `/api/results` and `/api/farmer-feed`.

## What each script does

| Command                     | Purpose                                                        |
| --------------------------- | -------------------------------------------------------------- |
| `data/synthetic_generator.py` | ~90 days of 30-min sensor data for `treatment`/`control` plots |
| `src/data_pipeline.py`      | clean (clip + interpolate) and feature-engineer the data       |
| `src/tune.py`               | `RandomizedSearchCV` with `TimeSeriesSplit` (no leakage)       |
| `src/train.py`              | threshold baseline, logistic regression, Random Forest, XGBoost |
| `src/evaluate.py`           | per-class metrics table + feature-importance plot              |
| `src/export_edge_model.py`  | joblib / ONNX export with file-size report                     |

## Model comparison table

`results/model_comparison.csv` contains accuracy, precision, recall and F1
**per class** on the held-out **chronological** test set, sorted by macro-F1.
The rows are sorted because accuracy alone is misleading when
`don't_irrigate` is the majority class. Every ML model should be compared
against the `baseline` (threshold rule) row — if an ML model can't beat a
simple `soil_moisture < X` rule, that is a finding worth reporting honestly.

## Interpreting the results

* **Splitting is chronological** (first 70% train, next 15% validate, last
  15% test). Random shuffling would leak future information into training and
  inflate accuracy.
* **Tuning uses `TimeSeriesSplit`**, not standard k-fold.
* **Feature importance** (`results/feature_importance.png`) uses built-in
  tree importances; past soil moisture and its lags are expected to dominate,
  matching the Theme C finding that soil-moisture history beats a full
  evapotranspiration model.
* **Edge deployability** is evidenced by the exported model size in KB, not
  just accuracy.

## Swapping in real field data

A future real dataset works **with no code changes** if it is a CSV with
exactly these columns:

| Column                | Type    | Notes                                    |
| --------------------- | ------- | ---------------------------------------- |
| `timestamp`           | datetime| ISO-8601, rows sorted chronologically     |
| `plot_id`             | string  | any string id per plot                   |
| `soil_moisture_pct`   | float   | 0-100                                    |
| `soil_temp_c`         | float   |                                          |
| `air_temp_c`          | float   |                                          |
| `air_humidity_pct`    | float   | 0-100                                    |
| `rainfall_mm_24h`     | float   | rolling 24h rainfall                     |
| `days_since_planting` | int     |                                          |
| `crop_growth_stage`   | string  | one of `establishment`/`vegetative`/`flowering`/`maturity` |
| `water_applied_l`     | float   | liters per irrigation event (0 when none) |
| `irrigated_next_flag` | bool    | label: was water applied in the next window? |

Then just:

```bash
cp your_field_data.csv data/raw/synthetic_sensor_log.csv
python -m src.data_pipeline && python -m src.train && python -m src.evaluate
```

Notes:
* The `time_of_day_*`, lagged-moisture, rolling-rainfall and growth-stage
  features are **derived automatically** — don't add them to your CSV.
* Rows with out-of-range readings are clipped to the bounds in
  `SENSOR_BOUNDS` (`src/data_pipeline.py`); missing values are linearly
  interpolated within each plot.
* If your sensor sampling interval differs from 30 min, pass
  `--interval-min <n>` to `src.data_pipeline` so the 3-hour rolling window is
  computed correctly. You can also use `--interval-min auto` and the pipeline
  will infer the median per-plot interval.
* Growth stages other than the four known ones will break the one-hot
  encoding — map them to the four-stage taxonomy or extend `GROWTH_STAGES`.

Four real-world datasets have been downloaded, converted, and wired into the
pipeline. Run any of them with:

```bash
python -m src.data_pipeline --dataset fbk --interval-min auto
python -m src.data_pipeline --dataset zenodo --interval-min auto
python -m src.data_pipeline --dataset unipr --interval-min auto
python -m src.data_pipeline --dataset unipr_evolving --interval-min auto
```

See [datasets.md](datasets.md) for source details and conversion notes.

## Edge deployment (Section 5.5)

* `src/export_edge_model.py` writes `edge/exported/best_model.joblib` and
  (best-effort) `best_model.onnx`, printing file sizes in KB.
* `edge/inference_service.py` is the Raspberry-Pi-side inference stub with a
  rule-based safety fallback when the model is unavailable or readings are
  out of range.
* For microcontroller-class devices, consider `micromlgen`/`m2cgen` to
  transpile a small tree ensemble into C for the ESP32, or run the model on a
  companion Pi that the ESP32 reports to.
